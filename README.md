# AI-помощник для подготовки товарных описаний

Прототип сервиса, который по данным контрольно-измерительного прибора собирает черновик
карточки товара для B2B-интернет-магазина: SEO-заголовок, SEO-описание, структурированные
характеристики, поисковые запросы и коммерческий блок для менеджера.

Проект сделан как тестовое задание для вакансии AI/LLM-разработчика (СОЮЗ-ПРИБОР).
Главный принцип: **модель не выдумывает характеристики**, а приложение это проверяет.

---

## 1. Что реализовано

| Требование ТЗ | Как реализовано |
| --- | --- |
| Приём данных через JSON | Вкладка «JSON»: проверка синтаксиса и структуры, понятные ошибки с номером строки |
| Приём данных через веб-форму | Вкладка «Форма»: название, производитель, характеристики, описание |
| Единый механизм обработки | Обе вкладки вызывают `parse_product()` и `generate_card()` — различается только сбор данных |
| Передача данных в LLM через API | `llm_client.py`, OpenAI-совместимый API (DeepSeek по умолчанию) |
| Черновик карточки товара | SEO-заголовок ≤ 70 символов, SEO-описание 800–1200 символов, характеристики, 3–5 запросов, коммерческий блок |
| Результат в удобном виде | Предпросмотр, Markdown и JSON с кнопками копирования и скачивания |
| Сообщение о недостающих данных | Поле `missing_data` от модели + автоматические предупреждения о пустых полях |
| API-ключ не в коде | Только `.env`, файл в `.gitignore`, в интерфейсе показывается лишь «задан / не задан» |
| Обработка ошибок | Ключ, 401/429/500, таймаут, сеть, пустой ответ, невалидный JSON, неверная структура |
| Запрет на выдуманные характеристики | Системный промпт + проверка чисел и единиц измерения по входным данным |
| Пометка «Данных нет» | Требование в промпте и пометка `NO_DATA` в коде |

## 2. Технологии

- **Python 3.10+** (проверено на 3.11)
- **Streamlit** — веб-интерфейс без отдельного фронтенда
- **openai** (официальный SDK) — единый клиент для DeepSeek, Ollama и других OpenAI-совместимых API
- **Pydantic 2** — проверка входных данных и структуры ответа модели
- **python-dotenv** — чтение `.env`
- **pytest** — тесты

Сознательно **не используются**: база данных, Docker, FastAPI, LangChain, векторные базы, RAG,
авторизация. Для этой задачи они не нужны и только усложнили бы запуск.

## 4. Установка

### Шаг 1. Python

Нужен Python 3.10 или новее. Проверить версию:

```bash
python --version
```

Создать и активировать виртуальное окружение в папке проекта:

```bash
# Windows (PowerShell)
python -m venv .venv
.\.venv\Scripts\Activate.ps1

# macOS / Linux
python3 -m venv .venv
source .venv/bin/activate
```

> Если PowerShell не разрешает активацию, выполните один раз:
> `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned`

Установить зависимости:

```bash
pip install -r requirements.txt
```

### Шаг 2. Настройка `.env`

Скопируйте образец и откройте его в редакторе:

```bash
# Windows
copy .env.example .env

# macOS / Linux
cp .env.example .env
```

Минимально нужно заполнить три переменные:

```dotenv
LLM_API_KEY=ваш_ключ
LLM_BASE_URL=https://api.deepseek.com
LLM_MODEL=deepseek-chat
```

Ключ DeepSeek берётся в личном кабинете на platform.deepseek.com. Файл `.env` добавлен
в `.gitignore`: ключ не попадёт в Git, в исходники и в логи.

### Шаг 3. Запуск

```bash
streamlit run app.py
```

Откроется браузер на `http://localhost:8501`. Если браузер не открылся — перейдите по адресу
вручную. Остановить сервер: `Ctrl+C` в терминале.

## 5. Два режима LLM

### DeepSeek (по умолчанию)

```dotenv
LLM_API_KEY=sk-...
LLM_BASE_URL=https://api.deepseek.com
LLM_MODEL=deepseek-chat
```

### Локальная Ollama (без интернета и без платного ключа)

```dotenv
LLM_API_KEY=ollama
LLM_BASE_URL=http://127.0.0.1:11434/v1
LLM_MODEL=qwen3:8b
```

Перед запуском модель нужно скачать: `ollama pull qwen3:8b`. Поле `LLM_API_KEY` для Ollama
не используется, но должно быть непустым — SDK требует значение.

Приложение само отключает системный прокси для локальных адресов (`127.0.0.1`, `localhost`),
иначе прокси Windows перехватывает запрос и возвращает ошибку 502.

Дополнительные параметры (необязательны): `LLM_TEMPERATURE`, `LLM_MAX_TOKENS`, `LLM_TIMEOUT`,
`LLM_JSON_MODE`.

## 6. Как пользоваться

### Вкладка «Форма»

1. Название товара и производитель — обязательны.
2. Технические характеристики — по одной на строку в формате `название: значение`.
   Разделителем может быть `:`, `=` или табуляция (удобно при вставке из таблицы).
3. Описание или выдержка из паспорта — свободный текст.
4. Кнопка «Сформировать карточку».

Пример заполнения характеристик:

```text
диапазон измерений: 0–1,6 МПа
класс точности: 1,5
присоединение: G1/2
диаметр корпуса: 100 мм
```

### Вкладка «JSON»

Вставьте JSON и нажмите «Только проверить JSON» (проверка без расхода токенов) или
«Сформировать карточку из JSON». Кнопки «Пример 1–4» подставляют готовые наборы: два
из тестового задания и два реальных товара из выгрузки каталога.

```json
{
  "name": "Манометр показывающий DM 02",
  "manufacturer": "Манотомь",
  "specs": {
    "диапазон измерений": "0–1,6 МПа",
    "класс точности": "1,5",
    "присоединение": "G1/2",
    "диаметр корпуса": "100 мм"
  },
  "description": "Прибор предназначен для измерения избыточного давления..."
}
```

Требования к JSON: объект с полями `name` (строка, обязательное), `manufacturer` (строка,
обязательное), `specs` (объект «характеристика»: «значение», необязательное), `description`
(строка, необязательное). Необязательные поля каталога: `article` (артикул), `price` (цена),
`offer_id` (ID предложения), `url` (ссылка). Они не попадают в характеристики и в промпт,
но показываются под результатом. Неизвестные поля игнорируются, числа в `specs` автоматически
приводятся к строкам.

### Результат

После генерации отображаются:

- предпросмотр карточки, вкладки Markdown и JSON с кнопкой копирования;
- кнопки «Скачать Markdown» и «Скачать JSON»;
- панель замечаний автоматических проверок;
- список сведений, которых не хватает (`missing_data`);
- блок «Что отправлено в модель» — можно посмотреть точный запрос.

## 7. Демонстрационные данные: происхождение

В техническом задании сказано, что кандидату предоставляются данные по двум товарам.
**Фактически в файле ТЗ есть только один пример — манометр DM 02**, причём его описание
обрывается многоточием («Прибор предназначен для измерения избыточного давления...»).
Второго товара в документе нет.

Поэтому:

| Файл | Происхождение |
| --- | --- |
| `examples/product_1_manotom_dm02.json` | Данные из ТЗ, перенесены дословно, включая обрезанное описание |
| `examples/product_2_artificial_pressure_transmitter.json` | **Искусственный набор**. Вымышленный прибор «ПД-100» и вымышленный производитель. Помечен полем `_comment` |
| `examples/results/*` | Реальный ответ модели на эти наборы; получены запуском приложения, вручную не редактировались |

Искусственный набор нужен только для демонстрации второго примера. Он не описывает
реальный товар и не должен использоваться как источник технических данных.

### Товары из выгрузки каталога

`feed.xml` — YML-выгрузка каталога СОЮЗ-ПРИБОР (47 978 предложений). Важная особенность:
в ней **нет ни одного `<description>`** и максимум два `<param>` (Артикул и Код товара).
Технических характеристик в выгрузке практически нет — только `name`, `typePrefix`,
`vendor`, `vendorCode`, `price` и `url`.

Из выгрузки взяты две позиции разных типов приборов:

| Файл | Offer ID | Что есть в XML | Чего в XML нет |
| --- | --- | --- | --- |
| `examples/catalog_rgk_ct12.json` | 194299 | Название, `typePrefix` (термометр, зонды), производитель RGK, артикул 779791, цена 15160, URL | Описание, диапазон температур, погрешность, питание, материал корпуса |
| `examples/catalog_oven_pd180.json` | 472728 | Название, `typePrefix` (датчик давления, вольтовый выход, энергосберегающее исполнение, назначение), производитель ОВЕН, артикул 159002, цена 13786, URL | Описание, диапазон давления, напряжение питания, точность, степень защиты |

Поэтому в `specs` попали только сведения, буквально следующие из `name` и `typePrefix`;
`description` оставлен пустым, а артикул, цена, Offer ID и URL хранятся в отдельных полях
`article`, `price`, `offer_id`, `url` и **не попадают в технические характеристики**.
Приложение показывает их отдельной строкой под результатом.

Для этих товаров данных объективно мало: ожидаемо короткое SEO-описание и предупреждения
о нехватке сведений. Это корректное поведение, а не ошибка генерации — выдумывать
характеристики запрещено. Результаты генерации по ним лежат в
`examples/results/catalog_rgk_ct12.md` и `examples/results/catalog_oven_pd180.md`.

Примеры результатов получены локальной моделью `qwen3:8b` через Ollama. Она заметно слабее
DeepSeek, поэтому примеры стоит читать с поправкой на модель:

- **Манометр DM 02.** В ТЗ к нему приложено описание из 57 символов, обрезанное многоточием.
  Модель честно сделала текст короче 800 символов, отметила отсутствующие характеристики
  значением «Данных нет» и попала в `missing_data`. Приложение показало предупреждение
  о нехватке длины — и это правильное поведение: добивать объём выдуманными характеристиками
  запрещено.
- **ПД-100 (искусственный набор).** Здесь данных больше, и карточка уложилась
  в 800–1200 символов, а проверки прошли без замечаний.

В неудачных прогонах модель добавляла отрасли, которых нет во входных данных («для отопления»,
«для нефтегазовой отрасли»), и подменяла отрицание. Промпт такие формулировки запрещает,
а проверки чисел, единиц и отрицаний ловят не всё: смысловые добавки без чисел видны только
при вычитке. Именно поэтому результат называется черновиком.

**Как перегенерировать примеры** (например, после подключения DeepSeek):

```bash
python scripts/generate_examples.py
# или только конкретные файлы:
python scripts/generate_examples.py catalog_rgk_ct12.json catalog_oven_pd180.json
```

Скрипт использует те же функции, что и веб-интерфейс, и перезаписывает файлы
в `examples/results/`.

## 8. Как устроен запрос к LLM

1. **Что отправляется.** Два сообщения: `system` — постоянная инструкция (роль, запреты,
   требования к полям, формат JSON), и `user` — данные конкретного товара
   (название, производитель, характеристики, описание).
2. **Системный промпт.** Задаёт «правила игры»: использовать только переданные сведения,
   не менять числа и единицы, не добавлять сертификаты и гарантии, отсутствующие данные
   помечать «Данных нет», вернуть строго JSON. Хранится в `prompts.py`.
3. **Пользовательский запрос.** Собирается функцией `build_user_prompt()`: список
   характеристик строками `- название: значение` и текст описания. Если описания нет,
   подставляется «не предоставлено».
4. **Что возвращает API.** Объект с `choices[0].message.content` (строка с JSON) и `usage`
   (сколько токенов потрачено). Приложение берёт только текст ответа.
5. **Как обрабатывается ответ.** `extract_json()` достаёт JSON (в том числе из ```json-обёртки),
   Pydantic проверяет структуру, затем `find_problems()` проверяет ограничения ТЗ и отсутствие
   выдуманных чисел. При нарушениях делается один повторный запрос с их списком. Если
   нарушения остались — карточка показывается с предупреждениями.

## 9. Какие проверки выполняет приложение

| Проверка | Что ищет | Реакция |
| --- | --- | --- |
| Длина SEO-заголовка | Больше 70 символов | Повторный запрос, затем предупреждение |
| Длина SEO-описания | Меньше 800 или больше 1200 символов | Повторный запрос, затем предупреждение |
| Количество запросов | Меньше 3 или больше 5 | Повторный запрос, затем предупреждение |
| Неизвестные числа | Число из ответа, которого нет во входных данных | Повторный запрос, затем предупреждение |
| Единицы измерения | «0–1,6 бар» вместо «0–1,6 МПа» | Повторный запрос, затем предупреждение |
| Текстовые значения характеристик | Слова в значении (материал, исполнение, интерфейс), которых нет во входных данных | Повторный запрос, затем характеристика исключается из карточки |
| Лимит «Данных нет» | Больше трёх таких характеристик | Повторный запрос, затем лишние переносятся в `missing_data` |
| Сертификаты, гарантия, «лучший», «№1» | Упоминание без основания во входных данных | Повторный запрос, затем предупреждение |
| Надёжность, стабильность, долговечность, «высокое качество» | Неподтверждённые обещания | Повторный запрос, затем предупреждение |
| Потеря отрицания | «агрессивные среды» вместо «неагрессивные» | Повторный запрос, затем предупреждение |
| Пропавшие характеристики | Значение из входа не попало в карточку | Повторный запрос, затем предупреждение |
| Незнакомые характеристики | Название, которого нет во входных данных | Предупреждение |
| Пустые входные поля | Нет характеристик, нет описания, описание короче 150 символов | Предупреждение |

Если после повторного запроса неподтверждённая характеристика осталась, приложение
**исключает её из таблицы** и пишет об этом в предупреждениях, а сведения о ней добавляет
в `missing_data`. Так выдуманное значение не выглядит как установленный факт.

Проверки чисел, единиц и слов — эвристики, а не формальное доказательство. Они ловят типичную
выдумку («класс точности 0,4», «материал — латунь»), но не заменяют вычитку менеджером:
приложение об этом честно пишет в интерфейсе и README.

## 10. Обработка ошибок

| Ситуация | Что увидит пользователь |
| --- | --- |
| Нет ключа в `.env` | «Не задан API-ключ. Скопируйте .env.example в .env…» |
| Ключ неверный (401) | «LLM отклонила API-ключ (ошибка 401)…» |
| Слишком много запросов (429) | «LLM ограничила частоту запросов…» |
| Ошибка сервера (5xx) | «LLM вернула ошибку HTTP 500: …» |
| Таймаут | «LLM не ответила за N секунд…» |
| Нет сети / неверный адрес | «Не удалось подключиться к LLM по адресу …» |
| Пустой ответ | «LLM вернула пустой ответ…» |
| Ответ не JSON / неверная структура | «Ответ модели не соответствует структуре карточки: нет поля …» |
| Некорректный JSON на входе | «Некорректный JSON: строка 4, колонка 3 — …» |
| Пустые обязательные поля | Список полей, которые нужно заполнить |
| Неверные типы в `specs` | «значение характеристики «…» должно быть строкой или числом» |

Ни одна из этих ситуаций не приводит к падению приложения с трейсбеком.

## 11. Тесты

Установить зависимости для тестов и запустить:

```bash
pip install -r requirements-dev.txt
pytest
```

Ожидаемый результат: `65 passed`. Что проверяется:

- `tests/test_models.py` — корректный ввод, числа вместо строк, пустые поля, неверные типы,
  битый JSON, JSON-массив вместо объекта, разбор характеристик из текста формы;
- `tests/test_generator.py` — успешная генерация, повторы при длинном заголовке и коротком
  описании, ловля выдуманного числа и подменённой единицы, выдуманное текстовое значение
  («латунь»), допустимые словоформы («сталь»/«стали»), лимит «Данных нет», неподтверждённые
  обещания надёжности и стабильности, потеря отрицания, неверное количество запросов,
  битый JSON от модели, пропавшие характеристики, выбор лучшей из двух попыток,
  форматы выгрузки;
- `tests/test_catalog_examples.py` — оба JSON-файла из каталога проходят входную валидацию,
  а цена и артикул не попадают в характеристики;
- `tests/test_llm_client.py` — отсутствие ключа, 401, 429, 500, таймаут, ошибка соединения,
  пустой ответ, пустой список вариантов, передача JSON-режима.

Все тесты используют заглушку вместо LLM и не ходят в сеть, поэтому выполняются меньше секунды
и не тратят токены.

**Что проверено реально.** Полный сценарий (`.env` → Streamlit/скрипт → API → разбор → проверки)

(результаты — `examples/results/catalog_*.md`). DeepSeek API в рамках этой сборки не вызывался:
ключа DeepSeek нет. Чтобы проверить его, достаточно заполнить `.env` и повторить запуск.

## 12. Принятые решения и промпт

- **Один путь обработки.** Форма и JSON сходятся в `parse_product()`, дальше логика общая —
  поведение не зависит от способа ввода.
- **Системный промпт с явными запретами и жёсткой схемой JSON.** Без few-shot: для двух
  примеров он не нужен, а правила сформулированы точнее, чем показывал бы пример.
- **JSON-режим API.** `response_format={"type":"json_object"}` уменьшает мусор вокруг JSON,
  но приложение всё равно разбирает ответ «с защитой»: снимает ```json-обёртку и ищет объект
  в тексте.
- **Проверки в коде, а не только в промпте.** Модель может проигнорировать инструкцию —
  поэтому длины, числа, единицы, отрицания и рекламные утверждения проверяются отдельно.
- **Проверяется каждое значение характеристики, а не только числа.** Если в значении есть
  слово, которого нет во входных данных, характеристика считается неподтверждённой:
  после повторного запроса она исключается из таблицы, а сведения о ней уходят в `missing_data`.
- **Лимит «Данных нет» соблюдается кодом.** Даже если модель вернула четыре таких пункта,
  в карточке останется три, остальные переносятся в `missing_data`.
- **Один повторный запрос.** Не бесконечные ретраи: две попытки. Если повторный ответ хуже
  первого, берётся первый; если повторный ответ сломан — первая карточка не теряется.
- **OpenAI-совместимый SDK.** DeepSeek, Ollama и vLLM меняются тремя строками в `.env`.
- **Без БД, Docker, FastAPI и фреймворков агентов.** Для прототипа это лишний слой.
- **Секреты только в `.env`.** В репозитории есть `.env.example` с фиктивными значениями,
  ключ не выводится в интерфейс и логи.

## 13. Ограничения проекта

- Один товар за запрос, без пакетной обработки и истории.
- Нет базы данных: результаты живут в памяти сессии Streamlit.
- Нет RAG и векторного поиска — модель видит только то, что ввёл менеджер.
- Нет авторизации и разграничения доступа: прототип для локального запуска.
- Streamlit не предназначен для промышленной эксплуатации и нагрузки.
- Нет потокового вывода (streaming) и подсчёта стоимости запросов.
- Длины текста проверяются по символам, а не по «смысловой полноте»: описание может быть
  в норме по длине, но слабее по качеству.
- Эвристики проверки чисел имеют ограничения: число, случайно совпавшее с входным,
  не будет поймано; нестандартная единица измерения может не распознаться.
- Смысловые добавки без чисел (отрасли, области применения, «подходит для…») проверками
  не ловятся: их видно только при вычитке.
- Проверка текстовых значений сравнивает слова по основе (первые пять букв), поэтому
  необычный синоним в значении характеристики может быть ошибочно признан выдумкой.
- Числа, входящие в обозначение модели (например, «0,025» в ПД180-ДВ0,025-0,25), формально
  присутствуют во входных данных и не могут считаться полностью выдуманными: приложение
  не угадывает, что это шифр модели, а не диапазон.
- В выгрузке `feed.xml` нет описаний и технических параметров, поэтому карточки по товарам
  каталога заведомо короткие: приложение показывает предупреждение вместо выдумывания данных.
- Качество результата зависит от модели: локальная 8B-модель слабее DeepSeek, особенно
  на длинных текстах.
- Демонстрационное описание манометра в ТЗ обрезано, поэтому карточка по нему заведомо
  беднее, чем была бы по полному паспорту.

## 14. Возможные улучшения

1. **RAG по каталогу и паспортам**: хранить PDF-паспорта, резать на фрагменты, искать похожие
   через векторную базу (pgvector, Qdrant) и подмешивать в промпт подтверждённые фрагменты.
2. **Локальные модели**: Ollama уже поддерживается; для нагрузки — vLLM на своём сервере.
3. **Интеграция с 1С-Битрикс**: REST-вызов сервиса из инфоблока, сохранение черновика
   в свойства элемента, публикация после проверки менеджером.
4. **FastAPI-обёртка** вместо Streamlit для интеграций и очередей.
5. **Кэширование** ответов по хэшу входных данных и **учёт стоимости** токенов.
6. **Оценка качества (evals)**: набор эталонных товаров и автоматическая метрика —
   сколько чисел выдумано, уложились ли в лимиты.
7. **Few-shot примеры** хороших карточек в промпте для стабильности стиля.
8. **Валидация по JSON Schema** на стороне API и строгий structured output.

## 15. Частые проблемы

**`streamlit: command not found`** — не активировано виртуальное окружение. Активируйте `.venv`.

**401 / «LLM отклонила API-ключ»** — ключ скопирован с пробелами или от другого провайдера.
Проверьте `LLM_API_KEY` и `LLM_BASE_URL`.

**502 при локальной Ollama** — системный прокси. Приложение отключает прокси для `127.0.0.1`
автоматически; если ошибка осталась, проверьте, что Ollama запущена (`ollama list`).

**«Модель вернула не JSON»** — некоторые локальные модели плохо соблюдают JSON-режим.
Попробуйте `LLM_JSON_MODE=false` или модель крупнее.

**Ответ короче 800 символов** — модель не стала додумывать (это правильное поведение).
Добавьте описание или характеристики и повторите запрос; приложение покажет предупреждение.

**Долгий ответ** — локальная модель на CPU может отвечать минутами. Увеличьте `LLM_TIMEOUT`.
