# Подготовка к техническому собеседованию

Этот файл — не часть приложения, а шпаргалка по проекту: что и почему сделано, как об этом
рассказать и какие вопросы могут задать. Важно: здесь отдельно отмечено, что **реализовано**,
а что является **планом развития**.

---

## 0. Короткий рассказ о проекте (2 минуты)

> «Нужно было сделать прототип, который по данным прибора готовит черновик карточки товара
> для B2B-каталога: SEO-заголовок, описание 800–1200 символов, характеристики, поисковые
> запросы и коммерческий блок. Я сделал приложение на Streamlit: данные вводятся в форму или
> вставляются JSON. Дальше данные проходят валидацию Pydantic, собирается промпт — системный
> с отдельными правилами и пользовательский с данными товара — и уходит в LLM через
> OpenAI-совместимый API. Ответ модели я не принимаю на веру: парсю JSON, проверяю структуру и
> главное — проверяю, что все числа и единицы измерения в ответе есть во входных данных.
> Если что-то нарушено, делается один повторный запрос с описанием ошибок; если и после этого
> нарушения остались, карточка показывается с предупреждениями. Ключ хранится только в .env.
> Покрыл это 65 тестами с заглушкой вместо LLM, а полный сценарий прогнал вживую на локальной
> модели через Ollama».

## 1. Архитектура приложения

Поток данных:

```text
Форма (Streamlit) ─┐
                   ├─> parse_product() ─> ProductInput (Pydantic)
JSON (Streamlit) ──┘                              │
                                                  v
                                     build_user_prompt() + SYSTEM_PROMPT
                                                  │
                                                  v
                                     request_completion()  ──> LLM API
                                                  │
                                                  v
                                 parse_card_response() (JSON + Pydantic)
                                                  │
                                                  v
                                     find_problems() / find_soft_warnings()
                                                  │
                             есть нарушения ──> один повторный запрос
                                                  │
                                                  v
                                       GenerationResult ─> UI: Markdown/JSON
```

Слои и ответственность:

| Слой | Файл | Ответственность |
| --- | --- | --- |
| Интерфейс | `app.py` | Собрать ввод, показать результат и ошибки |
| Валидация входа | `models.py` | Проверить типы, обязательные поля, разобрать JSON |
| Промпт | `prompts.py` | Правила для модели и формат данных |
| Транспорт | `llm_client.py` | HTTP-запрос, ретраи SDK, перевод ошибок |
| Оркестрация | `generator.py` | Повторы, проверки ответа, сборка результата |
| Настройки | `config.py` | `.env` → объект Settings |

**Почему так.** Каждый слой можно проверить отдельно: валидацию — тестами на словарях, логику
проверок — тестами с заглушкой вместо модели, интерфейс — глазами. Если завтра нужно будет
перейти на FastAPI, меняется только `app.py`.

## 2. Почему выбран такой стек

- **Streamlit** — веб-интерфейс на Python без HTML/JS. Для прототипа на 2–4 часа это самый
  быстрый путь, а менеджеру нужен именно экран с формой.
- **OpenAI SDK** — DeepSeek, Ollama, vLLM и большинство провайдеров предоставляют
  OpenAI-совместимый API. Один клиент — смена провайдера через `.env`.
- **Pydantic** — декларативная валидация: правила описаны рядом с полями, ошибки
  структурированы, можно показать их пользователю по-русски.
- **pytest** — стандарт, минимальный порог входа.
- **Без LangChain/LangGraph** — цепочка из двух шагов (запрос → проверка) не требует фреймворка.
  Фреймворк добавил бы абстракции, которые сложнее объяснить и отлаживать.
- **Без базы данных и Docker** — ТЗ прямо говорит, что это не требуется. Данные живут в сессии.

## 3. Как работает взаимодействие Python и LLM

1. Приложение формирует список сообщений:
   ```python
   [
       {"role": "system", "content": SYSTEM_PROMPT},
       {"role": "user", "content": build_user_prompt(product)},
   ]
   ```
2. `client.chat.completions.create(...)` отправляет POST-запрос на `/chat/completions`
   с моделью, температурой, лимитом токенов и `response_format={"type": "json_object"}`.
3. API возвращает JSON, где `choices[0].message.content` — строка с ответом модели,
   `usage` — расход токенов.
4. Приложение берёт строку и разбирает её как JSON. Pydantic проверяет поля.
5. Ответ проходит проверки, результат показывается пользователю.

Тонкости, о которых стоит помнить:

- `temperature=0.2` — меньше разброса, но полной детерминированности нет.
- `max_tokens` ограничивает длину ответа: если поставить слишком мало, JSON оборвётся.
- SDK сам повторяет запрос при сетевых сбоях (`max_retries=2`); повтор из-за нарушений
  формата делает уже `generator.py` — это разные вещи.
- Токены входа и выхода считаются по-разному и стоят по-разному; `usage` логируется.

## 4. Как обеспечивается защита от галлюцинаций

Три эшелона:

**1. Промпт.** Роль, явные запреты (не придумывать характеристики, не менять числа и единицы,
не добавлять сертификаты, гарантии, «лучший», «№1»), требование помечать отсутствующие данные
«Данных нет» и возвращать только JSON.

**2. Код.** Проверки после ответа:
- все числа из ответа должны встречаться во входных данных;
- единица измерения при числе должна совпадать с входной;
- каждое слово в значении характеристики (материал, исполнение, интерфейс) должно
  встречаться во входных данных; иначе характеристика исключается из карточки,
  а сведения о ней уходят в `missing_data`;
- слов вроде «сертификат», «гарантия», «поверка», «ГОСТ», «лучший», «надёжность»,
  «стабильность» быть не должно, если их нет во входных данных;
- не более трёх характеристик «Данных нет», остальное — в `missing_data`;
- характеристики из входа не должны пропасть из карточки;
- названия характеристик должны быть узнаваемы во входных данных.

**3. Человек.** Результат — всегда «черновик». Интерфейс показывает предупреждения и список
недостающих сведений, менеджер принимает решение о публикации.

Честная оговорка: пункт 2 — эвристики. Число, случайно совпавшее с входным, проверку пройдёт;
смысловая выдумка без чисел («подходит для пищевой промышленности») ловится только промптом
и вычиткой. В README это написано прямо.

## 5. Как проверяется корректность ответа модели

1. **Синтаксис.** `extract_json()`: снимает ```json-обёртку, пытается `json.loads`, при ошибке
   ищет подстроку от `{` до `}`.
2. **Структура.** `ProductCard.model_validate()`: обязательные поля, типы, непустые списки;
   `key_specs` принимается и как список, и как объект.
3. **Бизнес-правила.** `find_problems()`: длины, количество запросов, числа, единицы,
   запрещённые утверждения.
4. **Повтор.** Один повторный запрос с перечнем нарушений (не больше двух попыток всего).
5. **Финальный результат.** Если нарушения остались — они попадают в `warnings` и видны
   в интерфейсе и в выгрузке JSON.

## 6. Как обрабатываются ошибки API

В `llm_client.py` каждая ошибка SDK ловится отдельным `except` и превращается в `LLMError`
с русским текстом:

| Исключение | Причина | Сообщение |
| --- | --- | --- |
| `AuthenticationError` | неверный ключ | «LLM отклонила API-ключ (401)…» |
| `APITimeoutError` | модель не ответила вовремя | «LLM не ответила за N секунд…» |
| `APIConnectionError` | нет сети / неверный адрес | «Не удалось подключиться…» |
| `RateLimitError` | лимит запросов | «…ошибка 429…» |
| `APIStatusError` | 4xx/5xx | «…HTTP 500…» |
| `APIError` | прочие ошибки API | «Ошибка LLM API…» |
| любое другое | сеть, SSL, провайдер | «Не удалось получить ответ…» |

Интерфейс ловит `AppError` (общий предок) и показывает `str(exc)` — без трейсбеков.
Ключ никогда не попадает в текст ошибки и в логи.

## 7. Как добавить локальную LLM через Ollama

**Что уже есть.** Поддержка Ollama реализована на уровне клиента: достаточно поменять `.env`:

```dotenv
LLM_API_KEY=ollama
LLM_BASE_URL=http://127.0.0.1:11434/v1
LLM_MODEL=qwen3:8b
```

Одна деталь: для локального адреса приложение отключает системный прокси (`trust_env=False`),
иначе прокси Windows перехватывает запрос и возвращает 502. Это реальная проблема, с которой
я столкнулся при проверке.

**Что нужно для «настоящего» локального контура:**
- запускать Ollama (или vLLM) как сервис, лучше в Docker с GPU;
- хранить модели на отдельном диске и следить за памятью (8B в Q4 — около 5 ГБ VRAM);
- проверять здоровье сервиса (`/api/tags`) перед запросом;
- ограничить контекст и `max_tokens` под железо;
- для нагрузки — vLLM с батчингом вместо Ollama;
- учесть, что 8B-модель хуже держит длинные тексты и JSON, поэтому повторные запросы
  и проверки становятся ещё важнее.

## 8. Как развить приложение до RAG-системы

**Сейчас RAG нет.** Модель видит только данные, введённые менеджером.

Как бы выглядело развитие:

1. **Хранилище документов**: паспорта PDF, сертификаты, каталог. Разбор PDF → текст.
2. **Нарезка**: фрагменты по 500–800 токенов с перекрытием, с метаданными (товар, раздел).
3. **Индексация**: эмбеддинги (например, `bge-m3`, поддерживает русский) → векторная база
   (pgvector в PostgreSQL или Qdrant).
4. **Поиск**: по названию и характеристикам товара находим top-k фрагментов, желательно
   с фильтром по товару.
5. **Промпт**: в `user`-сообщение добавляются найденные фрагменты с указанием источника;
   системный промпт требует ссылаться только на них.
6. **Проверка**: те же проверки чисел плюс проверка, что утверждение подтверждено фрагментом.
7. **Метрики**: доля ответов с выдуманными числами, попадание характеристик в эталон,
   скорость поиска.

Важно: RAG не отменяет проверки — он уменьшает число случаев, когда модели не хватает данных.

## 9. Как интегрировать с 1С-Битрикс

**Сейчас интеграции нет.** Возможный путь:

1. Обернуть `generate_card()` в FastAPI-эндпоинт `POST /generate` (JSON на входе и выходе).
2. Из Битрикса вызывать его при сохранении элемента инфоблока (событие `OnAfterIBlockElementAdd`)
   или по кнопке в админке.
3. Результат складывать в свойства элемента: SEO-заголовок, SEO-описание, характеристики,
   поисковые запросы — в черновик, не в публикацию.
4. Публиковать только после подтверждения менеджером.
5. Аутентификация: сервисный токен в заголовке, ограничение по IP, журнал вызовов.
6. Ограничения: таймауты HTTP (генерация может занимать десятки секунд) → асинхронная
   очередь и статус «в обработке».

## 10. Ограничения текущего MVP

- один товар за запрос, без пакетной обработки;
- нет истории и базы данных — результаты живут в сессии Streamlit;
- нет RAG, векторного поиска, работы с PDF;
- нет авторизации;
- Streamlit — инструмент прототипа, не промышленный веб-сервер;
- нет streaming и подсчёта стоимости;
- проверки чисел и единиц — эвристики, возможны ложные срабатывания;
- качество зависит от модели; локальная 8B слабее DeepSeek;
- демонстрационное описание манометра в ТЗ обрезано, поэтому пример беднее реального паспорта.

## 11. Возможные вопросы и короткие ответы

**Почему не LangChain?**
Задача — два шага: запрос и проверка. Фреймворк добавил бы зависимости и абстракции без выгоды.
При росте до RAG и агентов его можно рассмотреть.

**Что будет, если модель вернёт 5000 символов описания?**
Проверка длины не пройдёт, уйдёт один повторный запрос с требованием сократить. Если не
помогло — карточка покажется с предупреждением, обрезать текст автоматически я не стал:
это может сломать смысл.

**Как вы гарантируете, что модель не выдумает характеристику?**
Не гарантирую полностью. Снижаю вероятность промптом и ловлю числа/единицы кодом. Финальная
ответственность — на менеджере, интерфейс об этом предупреждает.

**Почему проверяете числа, а не всю фразу?**
Числа — самая частая и самая опасная выдумка в технических карточках. Смысловые утверждения
проверить сложнее; для них пока есть промпт и вычитка.

**Что если во входных данных число записано как «1.5», а модель вернула «1,5»?**
Нормализую запятую и точку, лишние нули и пробелы — сравнение идёт по каноническому виду.

**Как хранится ключ?**
Только в `.env`, файл в `.gitignore`. В коде и логах ключа нет, в интерфейсе — только факт
«задан / не задан». В README есть `.env.example` с фиктивным значением.

**Как тестировали без реального API?**
65 тестов с заглушкой вместо LLM: проверяют валидацию, повторы, проверки ответа и обработку
ошибок. Отдельно был живой прогон на локальной модели через Ollama.

**Сколько стоит один запрос?**
Зависит от модели и длины. Вход — системный промпт (~600 токенов) плюс данные товара;
выход — до 2000 токенов. `usage` пишется в лог, но подсчёта денег в MVP нет.

**Что будет при двух одновременных пользователях?**
Streamlit создаст две сессии; запросы независимы. Но общего кэша и очереди нет — при нагрузке
нужен отдельный сервис (FastAPI + очередь).

**Почему бы не брать данные из 1С напрямую?**
В тестовом задании данных из 1С нет, а интеграция — отдельный слой. Сейчас вход — форма
или JSON, что и требовалось.

**Как бы вы улучшили качество текста?**
Few-shot примеры хороших карточек, более крупная модель, отдельный шаг «редактор» для
переписывания, оценка по эталонному набору (evals).

**Какие персональные данные обрабатываются?**
В текущем виде — никаких: только технические данные приборов. Ключ и текст запросов уходят
провайдеру LLM, это стоит учитывать при выборе облака или локальной модели.

**Почему у вас два вызова модели в худшем случае?**
Первый — генерация, второй — исправление конкретных нарушений. Больше двух не делаю, чтобы
не расти в стоимости и задержке.

**Что самое сложное было в задаче?**
Не сам запрос к модели, а проверка ответа. Нужно было придумать, как отличить выдуманное
число от настоящего, не сломаться на «1,5» против «1.5» и на словах вроде «02 предназначен»,
которые сначала принимались за единицу измерения. На живом прогоне выяснилось ещё одно:
модель переписала «неагрессивные среды» как «агрессивные» — числа на месте, а смысл
противоположный. Пришлось добавить отдельную проверку отрицаний.

## 12. Чего в проекте нет (не приписывать себе)

- RAG, векторной базы, работы с PDF — **нет**;
- интеграции с 1С-Битрикс — **нет**;
- FastAPI, Docker, PostgreSQL, Redis — **нет**;
- авторизации, истории, пакетной обработки — **нет**;
- вызова DeepSeek API в рамках этой сборки — **не было** (нет ключа);
- локальная LLM — **есть** как режим настройки, проверена на Ollama.

Эти пункты — направления развития, а не реализованный функционал.
